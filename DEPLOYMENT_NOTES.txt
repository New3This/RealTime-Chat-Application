REALTIME CHAT APPLICATION - DEPLOYMENT WALKTHROUGH

This note records the deployment decisions and troubleshooting from this
conversation. The final arrangement is one Render Web Service serving the
frontend, Express API, and Socket.IO from the same origin.

1. What the app needed

- The backend is a Node.js/Express server and uses Socket.IO for live chat.
- The app uses MongoDB, JWT cookies, and Cloudinary for uploaded images.
- A persistent Socket.IO server needs a long-running process. Redis can share
  Socket.IO events between server instances, but it does not make a short-lived
  serverless function keep an individual WebSocket connection alive.
- This is why a normal Web Service was chosen over a serverless backend.

2. Vercel was considered, then set aside

- The repository initially had vercel.json and this server startup guard:
      if (!process.env.VERCEL) {
          const port = Number(process.env.PORT) || 3000;
          server.listen(port, ...);
      }
- The Vercel guard around server.listen was later removed. The server now always
  listens on process.env.PORT (or local fallback 3000), which is the intended
  behavior for Render and local Node hosting.
- Do not add a fixed PORT environment variable on Render. Render supplies PORT
  for the running Web Service; the code reads it and uses 3000 only as a local
  fallback.
- Vercel's serverless execution is not suitable for this app's persistent
  Socket.IO connection. A Redis adapter would not change that limitation.
- vercel.json was deleted after deciding to deploy only on Render. Render does
  not use that file.
- Vercel-specific runtime branches were removed from backend/server.js,
  backend/socket/socket.js, and backend/middleware/upload.js. The server always
  listens on its configured port; uploads use UPLOAD_DIR or the local images
  directory.
- frontend/src/config.ts was made flexible for either deployment shape:
  VITE_API_URL can point at a separate backend, local development uses
  http://localhost:3000, and a production build without VITE_API_URL uses
  window.location.origin. The last behavior is what the final combined setup
  needs.

3. Render was selected

- Railway was discussed, but the requirement was a free service. Render was
  selected for its Node Web Service and WebSocket support.
- A free service may sleep when idle and may have a cold start or disconnect
  live connections during sleep/restarts. Free hosting is useful for learning
  and demos, but is not guaranteed to be always on.
- PORT is assigned by Render; it is not the public URL and must not be used by
  the browser. The browser uses the service's HTTPS URL.

4. First attempt: two Render services

- Backend Web Service:
  - Root Directory was set to backend. This made Render run its commands inside
    the backend folder, where backend/package.json and its lockfile are.
  - Build Command was npm ci. npm ci installs exactly what package-lock.json
    specifies and fails if the manifest and lockfile are inconsistent. It is
    generally preferred for automated builds over npm install, which can update
    the lockfile while resolving dependencies.
  - Start Command was npm start. backend/package.json defines start as
    node server.js. This launches the production Node process; npm run dev uses
    nodemon and is intended for local development instead.
  - Render's logs showed "Server is running on port 10000" and the service became
    live. This confirmed that the server started and bound to Render's PORT.
- Opening that backend service URL showed Cannot GET /. That was expected in
  the two-service setup: the backend did not serve a homepage yet; the frontend
  was a separate service.
- Frontend Static Site:
  - Root Directory was set to frontend so Render could find frontend's
    package.json and package-lock.json.
  - Build Command was npm ci && npm run build. The first command installs the
    frontend dependencies; the second runs the package's build script
    (tsc -b && vite build).
  - Publish Directory was dist because Vite writes the built site to
    frontend/dist, relative to the frontend Root Directory.
  - A React Router static site needs a fallback rewrite from /* to /index.html
    for direct visits or refreshes at /chat, /login, and /register. Without it,
    the static host looks for a physical file named /chat and returns 404.
- With separate services, the browser needed:
  - Frontend VITE_API_URL = the backend's public HTTPS origin.
  - Backend FRONTEND_URL = the frontend's exact public HTTPS origin.
  - The backend uses FRONTEND_URL for Express and Socket.IO CORS. Credentials
    require CORS to specify the exact origin and credentials: true.
- VITE_API_URL is a Vite build-time variable. It is included in the browser build
  and must contain only a public URL, never a secret.

5. Dependency and build errors in the two-service attempt

- npm ci initially failed with ERESOLVE. The project uses React 19, while
  @emoji-mart/react 1.1.1 declares a peer range that ends at React 18.
- The quick compatibility workaround was --legacy-peer-deps. This tells npm to
  proceed without enforcing that peer-dependency range; it does not prove that
  the package is officially compatible with React 19. The emoji picker should
  be tested in the running app. A more conservative alternative is to use
  React 18 and matching React type packages.
- Adding --legacy-peer-deps only to the custom Build Command did not fix the
  first Render attempt because Render's log showed an automatic dependency
  installation step before that command. NPM_CONFIG_LEGACY_PEER_DEPS=true was
  therefore suggested as a Render environment variable to affect that install.
- The next Vite build reported that @emoji-mart/react imported emoji-mart, but
  emoji-mart was not a direct dependency. emoji-mart was added to
  frontend/package.json and frontend/package-lock.json. After that, the
  frontend production build succeeded.
- npm audit reported dependency vulnerabilities during installation. Those
  notices were not the build failure and were not remediated in this deployment
  work.
- Vite also reported a JavaScript chunk larger than 500 kB. This was a warning,
  not a failed build; code splitting can be considered separately.

6. Browser errors and the auth-cookie/socket fixes

- The browser first showed CORS messages and 502 errors. A missing
  Access-Control-Allow-Origin header on a 502 can be a symptom of the backend
  failing, not necessarily proof that the configured CORS origin is wrong.
  Render's runtime logs were needed to see the server-side cause.
- Render logs showed a process crash at cookie.split(...): a Socket.IO handshake
  sometimes had no Cookie header, and the old middleware called split before
  checking for a missing header. The crash caused Render to restart the server,
  which in turn caused 502 responses.
- backend/socket/socket.js was changed to find the cookie named token even if
  other cookies are present, handle a missing token, verify the JWT, and call
  Socket.IO's next(error) for unauthenticated/invalid connections. A bad or
  missing cookie should reject that socket connection, not crash Node.
- Login succeeded with status 202, but a later protected request such as
  GET /chat/userbase returned 401 in Incognito. This meant the browser was not
  sending the auth cookie; it did not mean the password was rejected.
- In the two-service setup, the frontend and backend were on separate Render
  hostnames. SameSite=None; Secure cookie settings were added for HTTPS, but
  browsers can still block third-party cookies, especially in Incognito.
- backend/controller/controller.js now uses secure and SameSite=None cookie
  options when FRONTEND_URL begins with https://, and uses matching cookie
  options when clearing the token. This supports HTTPS cross-origin requests,
  but cannot override a browser's third-party-cookie blocking policy.
- Custom domains such as chat.example.com and api.example.com were discussed.
  They would need to share a registered domain and have separate CNAME records
  configured at the DNS provider. No domain was purchased and this path was
  abandoned.

7. Final arrangement: one Render Web Service

- The permanent no-domain solution chosen was to serve both frontend and
  backend from one Web Service. The browser now sees one origin for the HTML,
  API, Socket.IO, and auth cookie, avoiding the cross-site cookie problem.
- backend/server.js now resolves the frontend build directory relative to the
  server file, serves its static assets when frontend/dist exists, and serves
  index.html for /login, /register, and /chat. The explicit /chat page route is
  registered before the /chat API router so a browser page refresh does not get
  mistaken for an authenticated API request.
- The service Root Directory must now be blank (repository root), not backend.
  The build needs to reach both backend/ and frontend/. If Root Directory stayed
  at backend, the build could not reach the sibling frontend folder.
- Final Build Command:
      cd backend && npm ci && cd ../frontend && npm ci --legacy-peer-deps && npm run build
  - cd backend moves into the backend project.
  - npm ci installs the backend dependencies from backend/package-lock.json.
  - cd ../frontend moves to the sibling frontend project.
  - npm ci --legacy-peer-deps installs the frontend dependencies from its lock
    file while bypassing the React/emoji package peer-range conflict.
  - npm run build runs TypeScript compilation and Vite production bundling.
    Vite outputs frontend/dist, which the backend serves at runtime.
- Final Start Command:
      cd backend && npm start
  - This starts the backend package's production script (node server.js).
  - The process stays alive to handle HTTP and Socket.IO connections and listens
    on Render's injected PORT.
- The frontend config leaves VITE_API_URL unset in this combined service.
  Production then uses window.location.origin, which is the same Render URL
  that serves the backend. If VITE_API_URL were left pointing to another host,
  the built frontend would keep sending requests there.
- Set backend FRONTEND_URL to the combined service's exact HTTPS origin, for
  example:
      https://realtime-chat-application-gj04.onrender.com
  Express/Socket.IO still have their configured CORS policy; same-origin
  browser requests do not need a cross-origin CORS exchange. FRONTEND_URL also
  controls the HTTPS cookie settings.
- The previous Static Site's VITE_API_URL setting is separate from the
  combined Web Service and does not configure the combined build. Keep the old
  Static Site until the combined service is verified, then it can be stopped or
  ignored.
- The final Render environment should include the values the backend needs:
  MONGODB_URI, JWT_SECRET, FRONTEND_URL, and
  CLOUD_NAME/CLOUD_API_KEY/CLOUD_API_SECRET if Cloudinary uploads are used.
  Store secrets in Render, not in Git.
- Redis was later removed from this single-instance deployment. Socket.IO's
  default in-memory adapter handles users connected to this one process.
  Reintroduce a Redis adapter if multiple backend instances must share events
  and rooms; Redis is not needed merely because users have different IPs.
- No CNAME records, custom domain, or purchased domain are needed in this
  arrangement.

8. How to deploy and learn from the logs next time

- Make a code change locally and run the relevant build before deployment.
  The frontend build was verified with npm --prefix frontend run build.
- Commit and push the changes to the Git branch connected to Render.
- Render runs the Build Command first. Dependency, TypeScript, or Vite errors
  are build errors; the Start Command will not run until the build succeeds.
- After a successful build, Render runs the Start Command. A line such as
  "Server is running on port 10000" confirms the process started and bound to
  the host-provided port. The service URL becoming Live confirms deployment,
  not that every database/API/socket flow works.
- Test the public service URL at /, then log in, open /chat, refresh, and test
  the Socket.IO conversation flow. Incognito is useful for checking a clean
  cookie state now that frontend and backend share an origin.
- Browser DevTools Network shows request URL, status, response body, and
  cookies. Render's service Logs show server-side exceptions and restarts.
  Use both: a browser CORS message can hide an underlying 502, and a 401 on a
  protected route usually means the backend did not receive a valid cookie.
- Remember the deployment vocabulary:
  - Root Directory chooses the folder Render runs commands from.
  - Build Command installs dependencies and creates deployable assets.
  - Publish Directory is used by a Static Site; it is not used for this final
    Web Service because Express serves frontend/dist.
  - Start Command launches the live server process.
  - Environment variables configure a deployment without putting secrets in
    source code.
  - PORT is assigned by the host; the app must listen on that value.
  - Same-origin means the browser uses the same scheme, host, and port for the
    frontend and API; this is why the final cookie setup works better in
    Incognito than the two-service arrangement.
